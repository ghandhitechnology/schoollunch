# Bug Log - 2026-06-13

Scope: stress testing only. No fixes were applied in this pass.

## Confirmed Bugs

### 1. Startup refresh disables the whole app during slow network calls

- Severity: High UX
- Area: main UI startup / data refresh
- Repro:
  1. Mock `fetch_meal.fetch_meals` and `fetch_timetable.fetch_today` to sleep for 2 seconds each.
  2. Open `app_ui.show_app()`.
  3. Wait for startup auto-refresh to begin.
- Observed:
  - Every main action button becomes disabled while the background data refresh is in progress:
    - `커스텀 배경`
    - `찾기`
    - `지움`
    - `교사 명단 (이름 가림 해제)`
    - `설정 저장`
    - `배경화면 재생성`
    - `배경화면 적용`
  - With real request timeouts this can feel like a frozen or grey-screen app even though the Tk loop is alive.
- Expected:
  - Startup data refresh should not block unrelated navigation and editing actions.
  - At minimum, `커스텀 배경`, teacher roster, and settings controls should remain usable while data loads.

### 2. Corrupted config can expose impossible class values in the UI

- Severity: Medium
- Area: config validation / main UI
- Repro:
  1. Write config with `grade=999`, `class_num=999`.
  2. Open the main UI.
- Observed:
  - The class selector displays `999-999`.
  - The value is not clamped to the app-supported range.
- Expected:
  - Invalid class config should normalize to a supported class, currently one of `1-1` through `1-4`.
- Risk:
  - Invalid class values can drive invalid timetable requests and confusing generated wallpaper labels.

### 3. Multiple installed/built app bundles share the same bundle identifier

- Severity: Medium deployment / user confusion
- Area: packaging / launch behavior
- Evidence:
  - The following app bundles all report `CFBundleIdentifier = 하태욱 프로그램`:
    - `/Applications/하태욱 프로그램.app`
    - `dist/하태욱 프로그램.app`
    - `dist-macos/하태욱 프로그램.app`
  - Computer Use reported ambiguity between the same app copies.
- Observed:
  - It is easy to test or launch a stale copy while believing it is the current build.
  - Automation cannot reliably target the intended bundle by name.
- Expected:
  - There should be one clearly current deploy target, or unique bundle identifiers for installed/dev builds.

### 4. Custom Label-based buttons are visually clickable but weakly exposed to accessibility

- Severity: Medium accessibility / automation
- Area: UI controls
- Evidence:
  - Computer Use could visually see the controls but the accessibility tree only exposed the window/menu/title, not the internal app buttons as actionable buttons.
  - Coordinate clicking against the packaged app was unreliable in Computer Use after screenshot retrieval.
- Observed:
  - Controls such as `커스텀 배경`, `배경화면 재생성`, and `배경화면 적용` are not robustly discoverable as native buttons.
- Expected:
  - Important controls should be accessible through keyboard navigation and macOS accessibility APIs.
- Risk:
  - Screen readers, UI automation, and keyboard-only use are degraded.

### 5. Wallpaper apply status is boolean and does not verify all user-visible desktop states

- Severity: Medium
- Area: wallpaper apply UX
- Repro:
  1. Run live macOS wallpaper stress with two temporary images.
  2. Read `NSWorkspace.desktopImageURLForScreen_` after each apply.
- Observed:
  - The direct AppKit path worked for the primary screen and alternated paths correctly.
  - However, the UI only reports `배경화면 적용 완료` from a boolean return.
  - It does not show which file was applied or whether all monitors/Spaces visibly updated.
- Expected:
  - For a user-facing wallpaper feature, status should distinguish:
    - image regenerated
    - file copied to live path
    - AppKit applied to N screens
    - AppleScript fallback used
    - partial failure
- Risk:
  - This can appear inconsistent when macOS accepts the API call but a Space/monitor has not visually updated yet.
